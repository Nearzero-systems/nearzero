# Runner protocol (M3a)

How the control plane and the runner on every server talk (spec 25 D1 option C, D5). The schemas both ends validate with are in `packages/shared/src/runner-protocol.ts`; the runner is `runner/`, the control plane's side is `apps/control/src/runners/`.

## Shape of the link

- The runner opens **one WebSocket out** to the control plane and keeps it open: `GET /api/v1/runner/connect` with `Authorization: Bearer <credential>`. Servers behind NAT work; nothing listens on the server.
- Before each connection attempt the runner calls `GET /api/v1/runner/check` with the same header: `200` means connect, `401` means the credential was refused (the runner then tries a join token if it has one), anything else means "try again later".
- Every frame is one JSON object with a `type`. Each side validates every frame; a frame that doesn't parse closes the link with code 4003. Fields a side doesn't know are ignored.
- Reconnects back off from 1 s, doubling to 30 s, with ±25 % jitter. A successful welcome resets the backoff.
- On the Nearzero host the runner reaches the API at `http://nearzero-control:3000` over the internal network, and is never moved off it. That is the only plain address a runner uses, and only a runner in a container (`NEARZERO_RUNNER_CONTAINERIZED=true`) with a readable hand-off folder (`NEARZERO_RUNNER_HANDOFF_DIR`) uses it, on a single-label name; loopback isn't one (C4-16). That runner follows no `welcome.link`, `fallback` or `nextFingerprint`, whatever answers on the private network, and keeps no `control-link.json`.
- **Remote runners are always encrypted** (spec 31's decision, G3-01, C4-02 to C4-05). A remote runner never connects to, falls back to or follows a move to a plain `http://` address, or an `https://` IP address without the pinned fingerprint: its settings (`NEARZERO_CONTROL_URL`), `join http://…`, an empty `--fingerprint=`, a saved address and a welcome's `link` are refused, so its credential never crosses the network unencrypted and a runner whose only address is plain doesn't connect at all ("run setup again on the server"). Setup and the join command refuse when Nearzero has no encrypted address. The address, chosen by the control plane (`apps/control/src/runners/link.ts`), is the first of:
  1. an `https://` `NEARZERO_RUNNER_CONTROL_URL` set outright, to a host name (a plain one, or an IP address, which a runner can check only with a fingerprint, is ignored, with a line in the start log);
  2. `https://<console hostname>` (set at install or under About Nearzero) once the host's router holds a valid certificate for it; the installer's console route sends `https://<console>/api/v1/runner/*` straight to the API (port 3000), so ports 3000 and 4321 can be blocked;
  3. **the runner link's own TLS port**, `https://<public IP>:3443` (`NEARZERO_RUNNER_LINK_PORT`), served by the control plane itself with a self-signed certificate (ECDSA P-256, valid until 9999) that it makes at its first start and keeps in the `nearzero-runner-link` volume (`NEARZERO_RUNNER_TLS_DIR`): restarts, upgrades and reruns of the installer keep it, and a pair that can't be read or doesn't belong together stops the port rather than being replaced. Setup writes `NEARZERO_CONTROL_FINGERPRINT=sha256:<hex>` (the certificate's SHA-256, DER) beside `NEARZERO_CONTROL_URL`, and the join command reads `sudo nearzero-runner join https://<ip>:3443 --fingerprint sha256:<hex>`. That port serves the runner's routes and `/api/v1/health` only, on every address even when the console is bound to 127.0.0.1;
  4. the console's hostname without a valid certificate yet, when the install has no TLS port (as before).

  Every remote runner also keeps 3, with its fingerprint, as its **fallback** (C4-06): setup writes `NEARZERO_CONTROL_FALLBACK_URL` and `NEARZERO_CONTROL_FALLBACK_FINGERPRINT=sha256:<hex>` when it gives the domain, every welcome to a remote runner carries `fallback { url, fingerprint }`, and the runner keeps it in `control-link.json`. After five failed connections in a row to the address it uses, the runner tries the fallback (or the address its settings give, when that is encrypted and different); never a plain one, and never a fingerprint that was replaced (below).

  **The newest pin wins** (C4-12). `control-link.json` is used only while the settings are the ones it was saved with: the address, its fingerprint and the fallback. When setup runs again and writes anything else, its settings are newer and win, and the saved addresses go. Otherwise what the control plane said last wins over the settings: when a welcome gives a fingerprint for an address, every other fingerprint the runner knows for that address (from its settings, its saved file, the address in use) is **retired** and never accepted again from anywhere, also after five failures. Retired fingerprints are kept in `control-link.json`.
- **How the runner checks the address** (C4-01, C4-03). The runner opens every connection itself, over `node:tls`, and checks the certificate on that very connection before it writes a single byte: the WebSocket (`runner/src/link/socket.ts`, RFC 6455), and its requests (`runner/src/link/http.ts`, HTTP/1.1, one per connection: check, enroll, uploads, migration archives, whose answers stream; an answer must give its length or come in chunks, since a close-delimited one can be cut short by anyone on the path, and a body that brings nothing for 60 seconds while it is read stops the request, C4-17). With a fingerprint, only the certificate with exactly that SHA-256 (or the next one while the pair is replaced) is accepted, whoever signed it, and only over TLS 1.3, which has no renegotiation: Bun's client ignores `minVersion`, so the runner checks the negotiated version itself and refuses anything older before writing (C4-15); renegotiation is turned off on every link connection too. Without one, a public authority's certificate for exactly that host name; never an IP address, which Bun's TLS client doesn't check against a certificate. Bun's own clients aren't used for this: its `fetch` with `tls.ca` trusts every public authority too and calls `checkServerIdentity` only after it has written the request, and its WebSocket client checks no host name, so a certificate a public authority issued for any name would have received the credential or the join token.
- **Moving a runner.** A runner says where it is in `hello.link` (older runners don't). When that isn't where it should be, its welcome carries `link { url, fingerprint }` and nothing else crosses that connection: no resumed output, results, commands or routes, even its own messages other than heartbeats are ignored. A move is only ever to one of two kinds of address (`runnerMoveTarget`): `https://<host name>`, checked against a public authority and that name, or the pinned TLS port with its fingerprint; it can come only over an encrypted link whose certificate was checked. A welcome offering anything else closes the link as a protocol error (4003) and the runner stays. The runner leaves (4006), connects to the new address, and once welcomed there keeps it in `<state dir>/control-link.json` (0600, beside its credential) with the configured address and fingerprint it came from; setup run again with another address wins over the saved one. A new address that doesn't answer is declined (`hello.link.declined`): the runner goes back and is served there. The hub doesn't cut it off to retry (C4-09); the runner checks each declined address in the background every five minutes with a check request alone, and moves once one answers. Every minute the control plane reconnects runners that aren't where they should be and haven't declined it, so runners move to the console's domain once its certificate is valid, without setup.
- **A runner on plain HTTP gets no work** (C4-05). A remote runner whose `hello.link` is `http://`, or an older runner that reached Nearzero unencrypted, is `refused` (`unencrypted`, close 4007) whether or not there is an encrypted address to move it to, and never moved from there: its credential already crossed the network in clear. The server's page shows why (`runner.link_problem`): run setup again on the server, or its join command.
- **Replacing the link certificate** (C4-10). `sudo nearzero runner-link rotate` makes the next pair beside the current one (`link.next.crt`, `link.next.key` in the `nearzero-runner-link` volume) and prints its fingerprint. Within a minute the control plane gives every connected remote runner that fingerprint over its current, still-valid link (it reconnects each one once; its welcome carries `nextFingerprint`), and others when they next connect. Runners accept both certificates from then on, keep the next one in `control-link.json`, and report it in `hello.link.next` and in heartbeats (`runner.link_next`). `sudo nearzero runner-link status` lists the servers that don't hold it yet; `sudo nearzero runner-link switch` refuses while one doesn't (unless `--force`, which names the servers that need setup again), puts the next pair in place and restarts the control plane, whose welcomes then carry the new fingerprint. Until the restart the running control plane keeps announcing the new fingerprint as the next one, so a runner that reconnects in between keeps it (C4-13). A runner welcomed with the new fingerprint retires the old one for good, its settings' copy included: after the switch the old key is accepted by no runner that has reconnected since, which is what replacing a leaked key needs. A runner that lost its state folder, or never reconnected, still has the old fingerprint in `runner.env`: when the old key leaked, run setup again on those servers (status lists them). The switch writes every file under a temporary name and renames it, the key first; one interrupted between the two is finished by running `switch` again, and until then the control plane's start says so (C4-14). The replaced pair is kept as `link.previous.*` (with `link.previous.json`: its fingerprint and when it was replaced) only until every server has reconnected to the new one, or for 7 days, then the control plane removes it. `runner-link cancel` drops a pair that isn't wanted. Rotate, switch (with the servers a forced one cut off) and cancel are in the audit log, and so is the removal of the replaced pair. At start, a certificate whose key is gone, or a pair that doesn't belong together, stops the TLS port with the files named instead of making a new pair; only a key without its certificate (an interrupted first start, which nobody can have pinned) is made again.

## Credentials and joining

| Thing | Form | Stored | Lifetime |
| --- | --- | --- | --- |
| Join token | `nzj1.<token id>.<secret>` | SHA-256 of the secret, in `runner_join_token` | One use; 1 hour (24 hours for the host's handoff token) |
| Runner credential | `nzr1.<runner id>.<secret>` | SHA-256 of the secret, in `runner.credential_hash`; on the server in `<state dir>/credential`, mode 0600 | Until rotated or revoked |

- `POST /api/v1/runner/enroll` `{ joinToken, runnerVersion, protocol, minProtocol, system? }` trades a join token for a credential: `201 { serverId, serverName, credential }`. The token is marked used in the same transaction that issues the credential, so two runners racing with one token can't both join. A runner outside the protocol window is refused before the token is used.
- Joining again (a new join command, or setup run again) **rotates** the credential: the old one stops working at once and a runner still connected with it is disconnected (code 4002).
- Deleting the server, or `POST /servers/:id/runner/revoke`, revokes it.
- Secrets are compared in constant time (`constantTimeEqual`), also when no row matches, so a wrong id and a wrong secret take the same time (spec 22.4 rule 7, gap G7).
- **The host enrolls itself.** At every start the control plane writes a fresh one-time join token to `NEARZERO_RUNNER_HANDOFF_DIR/host-join-token` (the `nearzero-runner-handoff` volume, mode 0640, group 10001) and drops older unused host tokens. The host's runner, which runs with every capability dropped and the control plane's group, reads it only when it has no working credential.

## Hello, welcome and the version window

1. Runner → `hello`: `runnerVersion`, `protocol` (the newest it speaks), `minProtocol` (the oldest), `startedAt`, `system` (spec 14.1 system information), `checks` (docker, network, router, routerDirectory), `streams` (each open stream with the output it still holds: `firstOffset`, `endOffset`, `ended`) and `commands` (still running, or finished with a result not yet received).
2. The control plane agrees on `min(runner.protocol, control.protocol)`. Below `RUNNER_PROTOCOL_MIN_SUPPORTED` it answers `refused { reason: "runner_outdated", message }` and closes with 4001; the message says to run setup again on the server's page, which updates it (there is no in-place **Update runner** yet, G3-05), and the server's page shows the runner as `update_needed`. A runner whose `minProtocol` is above the control plane's gets `reason: "control_outdated"` (update Nearzero). The refused runner waits 5 minutes before asking again.
3. Control → `welcome`: the agreed `protocol`, `controlVersion`, the `serverId` (a server id, or `host`), `serverName`, `publicIPv4` (for the certificate hold's DNS check), `heartbeatIntervalMs`, and:
   - `resume`: for each stream the control plane still follows, the offset it has stored;
   - `close`: streams nobody follows any more (the runner stops them; any open stream not in `resume` is stopped too);
   - `received`: command ids whose results the control plane already has.
4. Then, for each command the control plane still waits on (C2-01): one the runner lists in `hello.commands` is followed on (its result comes); one it never received goes again; one that changes nothing (`system.info`, the inspections and lists, `router.files`, certificate and DNS status) or is resume-only goes again even to a restarted runner. Any other command that was acknowledged, or delivered to an earlier runner process (`startedAt` differs), is reported lost ("The server's runner restarted while this was running…") and never started again. Then the control plane cancels running commands nobody waits for, sends `router.sync` with every route the server should have, and marks the server ready once all mandatory checks pass (spec 9.4).

**Long work across a control-plane restart (B2-20, spec 23.1).** Work a job started with a key (a task run, a backup or a restore) has ids made from it: the command `w:<key>` and its stream `w:<key>.out`. When the control plane stops, it stops waiting without stopping that work (no `cancel`, no `stream.close`), and its jobs stay queued. After a restart, keyed commands and streams in a runner's `hello` that this process doesn't follow are kept, not cancelled: their streams are resumed from the oldest output the runner still holds, a result that arrives is kept, and finished ones are left out of `received`. The job's next attempt follows the work again by its key with a `command` carrying `resumeOnly: true`, which a runner answers by following a command it is running or resending a result it holds, and otherwise with `not_found` ("isn't running on the server any more"): it never starts one. The job then records the real result, or that the work was lost to the restart. Keyed work no job follows within 10 minutes is cancelled with its stream, as unkeyed work is at once. A deploy doesn't follow its build: it starts again from the beginning on its next attempt, so its old build is cancelled.

A newer connection for the same runner replaces an older one (close 4000).

## Heartbeats

The runner sends `heartbeat { seq, at, next? }` every 10 s (`next`: the next link certificate's fingerprint it holds, C4-10) and the control plane answers `heartbeat.ack { seq }`. Either side treats 35 s of silence as a dead link (close 4004). Bun's WebSocket pings run underneath.

## Commands

Control → `command { commandId, kind, params, timeoutMs?, streamId? }`. The runner answers `ack { commandId }` at once (no ack within 15 s fails the command), runs it, and sends `result { commandId, ok, data | error }`. The control plane confirms with `result.received`; until then the runner keeps the result in an outbox and sends it again after a reconnect. A command id that arrives twice is acknowledged again and not run twice. `cancel { commandId }` aborts it. Across a reconnect the control plane never sends an acknowledged command to a new runner process (see the hello, step 4).

Errors carry a machine `code` (`invalid`, `not_found`, `conflict`, `docker_unavailable`, `timeout`, `cancelled`, `unsupported`, `failed`) and a `message` for people. A runner that doesn't know a command answers `unsupported` with "This runner (version …) doesn't know the command … Update the runner."

## Streams and resume

- A streaming command names a `streamId` chosen by the control plane. Output goes as `stream.data { streamId, offset, data }`: `offset` is the byte position of the chunk's first byte in the whole stream, `data` is base64, at most 64 KiB before encoding. Log, build and pull output is sent in whole lines where possible.
- The control plane answers `stream.ack { streamId, offset }` with everything it has received; the runner forgets output before it.
- While the link is down the runner keeps reading (a log follow keeps following) and holds up to 8 MB per stream. On reconnect, `welcome.resume` says where the control plane stopped, and the runner sends from exactly that offset.
- **Flow control** (C4-07). The link reports what it holds unsent (`bufferedAmount`). Above 4 MB stream output and metrics aren't handed to it: they stay in their own bounded buffers (the oldest output goes first, as when the link is down, and the control plane sees a gap) and are sent once it drains below 2 MB. Results, acknowledgements and heartbeats still go. A send that would take the link past 32 MB unsent drops the connection instead of queueing (results wait in the outbox and streams resume from their offsets), so a control plane that stops reading can't make the runner's memory grow.
- The control plane places every chunk by offset: a repeated chunk is dropped, an overlapping one is trimmed, and a jump forward (the runner had to drop output) is recorded and shown to viewers as a gap.
- `stream.end { streamId, offset, exitCode?, error? }` ends a stream at its final length. `stream.input` (base64) and `stream.resize { cols, rows }` go to a terminal; input that arrives before the process is ready is delivered when it is. `stream.close` stops a stream.
- The control plane keeps the last 2 MB of each stream for viewers who reconnect, stops streams nobody has watched for 30 seconds, and keeps ended ones for 5 minutes.

Browsers follow streams as server-sent events (see `docs/api/servers.md`); each `output` event's id is `<streamId>:<offset>`, so `Last-Event-ID` resumes exactly where the browser stopped.

## State and metrics

- `state { at, containers, router, checks }`: every container with only its `dev.nearzero.*` labels, the router's state (running, image, route count, held hostnames with reasons, last error, and `http3 { enabled, port, blockedBy }` once the router was checked: added in round 2, older runners leave it out) and the checks. Sent after the welcome, 1 s after any container event or router change, and every 30 s.
- `metrics { samples }`: one sample every 5 s (CPU %, memory used/total, root filesystem used/total, uptime; spec 14.1), plus `diskAvailableBytes`, df's "Available" (statfs `f_bavail`), so Storage usage reads used / (used + available) as df does (30c R3-34). It is optional: older runners don't send it, and their samples read used / total. The root filesystem is the server's own: `/` on a server, and on the Nearzero host, whose runner runs in a container, the filesystem of `NEARZERO_HOST_ROOT_PATH`, one host file (`/etc/passwd`) bound read-only into the runner by `installer/compose.yml`, so the runner gains nothing it could write. Samples taken while the link is down are kept for an hour and sent together. The control plane stores them in `server_metric` for 2 days. Each message also moves the server's CPU and memory alerts (docs/api/monitoring.md).

## Router files

The runner owns the router on its server: Traefik v3 with the file provider, entry points `web` (:8080) and `websecure` (:8443) with the host's 80/443 published onto them, ACME HTTP challenge, all capabilities dropped, read-only root filesystem, running as the owner of its configuration folder. It is recreated only when its settings' fingerprint (label `dev.nearzero.router-config`) changes; the old one is kept until the new one runs, and restored if it doesn't. It is checked every minute and started again when stopped.

**HTTP/3 (R3-22).** `websecure` also serves HTTP/3: the server's UDP HTTPS port (443) is published onto :8443/udp, and `http3.advertisedPort` makes the `Alt-Svc` header of HTTPS answers name the published port. Before it creates the router, unless the running router already publishes that UDP port, the runner looks for something else holding it: another container that publishes it (by name), or a program with a socket on it in `/proc/net/udp` or `udp6` (by its process name). A runner set up on a server reads the server's `/proc`; the Nearzero host's runner, which runs in a container, asks a short-lived helper container (`nearzero-router-udp-check`: the router's image as root in the host's network and process namespaces, all capabilities dropped but reading other processes' descriptors, read-only root filesystem, nothing mounted) that only reads. When the port is taken, or Docker refuses to publish it at start anyway, the router starts without HTTP/3 instead of failing, the state's `http3` says who holds it, and the server's details show "HTTP/3 is off: UDP port 443 is in use by <program>". That decision is looked at again every 5 minutes while the router runs without HTTP/3.

Each route is one file, `route-<key>.yml`, written atomically (temporary file, fsync, rename). `router.sync` leaves exactly the given routes; only `route-*.yml` and `nearzero-middlewares.yml` belong to the runner, so the installer's `console.yml` is never touched. Hostnames and paths are checked by the schema before they reach a rule, so nothing can break out of Traefik's rule syntax.

**Certificate hold (spec 10.7).** A route asks for `letsencrypt` (the default), `hold` or `none`. For `letsencrypt`, each hostname is checked first: names no public authority issues for (`localhost`, `.local`, `.test`, IPs, single labels), an unknown server address, no A record, an A record elsewhere, or a failed lookup (10 s timeout) keep it **held**: its router serves Traefik's own placeholder certificate on HTTPS and serves plain HTTP without redirecting, and Let's Encrypt is never asked. Held hostnames are checked again a minute after the runner starts and every 5 minutes, and when asked (`router.check-holds`); one whose DNS now points here gets `certResolver: letsencrypt` and an HTTP→HTTPS redirect.

**Back-off and uploads (spec 10.7, M4).** Before the DNS check, the runner asks its certificates part about each hostname: one an uploaded certificate covers gets a router with `tls: {}` (the router picks the uploaded certificate by name) and the HTTPS redirect; one in back-off is held like above. The router logs as JSON (`--log.format=json`), and the runner follows that log for "Unable to obtain ACME certificate" entries: after 3 failed validations within an hour the hostname is held until an hour after the first, and a rate limit holds it until its retry-after time (or an hour). Holds start the moment the failure is logged, and are kept in `<state dir>/certificates.json` across restarts; the 5-minute check releases them when they end. `certificates.retry` lifts the back-off for earlier failures and holds the hostname for 3 seconds before releasing it, which the router sees as a new configuration and asks again. `certificates.status` reads `acme.json` from the router's certificates volume through Docker's archive endpoint. Before the router is created, and once each time the runner starts, a one-off container (`nearzero-router-certificates-owner`: the router image as root with only the chown rights, no network) gives that volume and what is in it to the router's user, so a router running as a non-root SSH user can write `acme.json`; when it had to change an owner under a running router, the router is restarted to reopen its store. Uploaded certificates are files under `certificates/` in the router folder (keys 0600, owned by the folder's owner) and `nearzero-certificates.yml`, which lists them. `NEARZERO_ACME_CA_SERVER` and `NEARZERO_ACME_CA_CERTIFICATES` point the router at a private ACME server (the end-to-end suite uses Pebble).

**The built-in DNS server.** `dns.apply` writes the Corefile and `zones/*.zone` into `NEARZERO_DNS_DIR` and keeps `nearzero1-dns` (CoreDNS on 1053, the host's 53 published onto it, every capability dropped but binding) running, creating it when the install didn't; with no zones it stops it, and removes it if the runner made it. CoreDNS reloads changed files within seconds. `dns.status` answers whether it runs and the SOA serial it serves for each zone.

## Close codes

| Code | Meaning |
| --- | --- |
| 4000 | Replaced by a newer connection for the same runner |
| 4001 | Protocol outside the supported window |
| 4002 | Credential revoked or rotated |
| 4003 | A frame outside the protocol |
| 4004 | No heartbeat for 35 s |
| 4005 | The control plane is stopping |
| 4006 | Closed on request (a forced reconnect, or a move to another address) |
| 4007 | Refused: a remote runner that can reach the control plane only unencrypted |

## Changing the protocol

- Adding an optional field, a new command kind, or a new optional message: no new version. Older runners answer unknown commands with `unsupported`.
- Changing a message's meaning, or making a field required: raise `RUNNER_PROTOCOL_VERSION`, keep speaking the old version while it is inside the window, and raise `RUNNER_PROTOCOL_MIN_SUPPORTED` only in a release whose notes say to update runners.

## Limits of this version

- One control-plane process holds the runner connections (the install runs one). Running several would need routing commands and streams through PostgreSQL's NOTIFY, as the live-update design in ARCHITECTURE.md describes.
- Streams are followed in memory; a control-plane restart loses the viewers' replay window (keyed work goes on and its jobs follow it again, see above; a viewer reconnecting opens a new stream).
