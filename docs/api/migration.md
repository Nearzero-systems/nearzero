# Moving a 0.1.x install to 1.0

The 1.0 side of decision D3: reading the export bundle the final 0.1.x release writes, importing it, moving every service onto the 1.0 runner, rolling back and finalizing, and the installer finding a 0.1.x install. Implements spec 29 (all, 29.2a included) and the bundle contract of spec 29a, with 03.2–3.4 (the installer and the `nearzero` command), 23.3–23.4 (upgrades, secrets) and 25 D3.

Code: `apps/control/src/migration/` (reader, records, import, report, move, command line, old webhook paths, old console addresses), `apps/control/src/security/legacy-passwords.ts`, migrations `0650_migration_import.sql`, `0651_migration_webhooks_and_volumes.sql` and `0652_migration_console_paths.sql`; the console's `src/middleware.ts`, `lib/legacy-lookup.ts` and `lib/legacy-paths.ts`; runner commands in `runner/src/migration/` with their schemas in `packages/shared/src/runner-migration.ts`; the installer's section "Moving a 0.1.x install" in `installer/install.sh` and the `import` / `migrate` commands in `installer/nearzero`.

## The bundle

The byte layout (`NZEXPORT`, the header length, the clear JSON header, the AES-256-GCM ciphertext with everything before it as additional data, the 16-byte tag), the manifest and every record kind's fields are spec 29a. The reader (`openBundle` in `migration/bundle.ts`) refuses, each with a plain message and nothing imported:

| Case | Message |
| --- | --- |
| Not an export | "This file isn't a Nearzero export. Make one on the 0.1.x server with: sudo nearzero export" |
| Wrong passphrase, or any byte changed after export (the GCM tag covers the header too) | "Wrong passphrase, or the bundle was changed." |
| A header asking for scrypt N above 2^20 (or not a power of two), r above 32 or p above 16 | "This export asks for key settings Nearzero doesn't accept …" |
| A newer bundle format (header or manifest) | "This export uses bundle format N, and this version of Nearzero reads format 1. Update this server to the newest 1.0 release, then import again." |
| A file that doesn't match its manifest SHA-256 or size, a listed file missing, an unlisted file | "<file> doesn't match the checksum in the export's manifest, so the export was changed or damaged. Export again on the 0.1.x server." (and the like) |
| Larger than 2 GB | "This export is larger than 2 GB, which is more than Nearzero can open." |

The plain archive exists only in memory; nothing decrypted is written to disk. `createBundle` in the same file is the reference writer the tests build their fixtures with.

### The optional fields of 29a.9 and 29a.9.1

29a.9 names what these fields hold but not every shape, so `migration/legacy-fields.ts` reads the plain forms an exporter is likely to write and ignores anything else (an unknown workload kind is left alone, never guessed at). Without them:

| Where | Field | Read as | Without it |
| --- | --- | --- | --- |
| manifest | `installId` | The 0.1.x install the bundle comes from. A bundle whose id differs from an earlier import's is refused, nothing imported: "This export comes from a different 0.1.x install than the one imported here before, so their records can't be mixed. Import it into a fresh Nearzero 1.0 install." (exit 1) | Accepted (an older exporter) |
| `services.jsonl` | `legacy: { kind, name }` | The 0.1.x workload the service replaces: `swarm-service`, `swarm-stack`, `container` or `compose-project` | Derived from `appName`: a Swarm service of that name; for Compose, the Compose project (format `Compose`) or the Swarm stack (format `Stack`) of that name |
| `services.jsonl` | `servicePort` | The app's container port | The first hostname's port, else 3000 |
| `services.jsonl` mounts | `containerPath` (a file mount: `containerPath` and `content`) | Where the mount goes in the container | The older `path` / `filePath` |
| `servers.jsonl` | `legacy` | The 0.1.x router on the server, stopped before it is set up again (it holds 80 and 443): `{ container }`, `{ service }`, a name alone (a container), or `[{ kind, name }]` | Nothing is stopped; setup stops at its port check while something else holds 80 or 443, and the server's services stay on 0.1.x |
| `install.json` | `controlPlane` | What runs the 0.1.x control plane on the host: a list of `{ kind, name }`, kind `container`, `swarm-service` or `compose-project` (anything else is left out). Exactly these stop before 1.0 starts, start again on rollback and are removed by finalize | The installer stops nothing; when 4321, 3000, 80 or 443 is still held it puts everything back and stops |
| `install.json` | `controlPlaneDetails` | `{ composeProject, folder, ports, composeFiles, envFile }` (a folder must be a plain absolute path; files are names inside it): named in the dry-run report ("The 0.1.x control plane (Compose project …, in …, holding ports …): … stop when the move starts, and rollback starts them again."), and printed by `migrate control-plane` as `project`, `folder`, `composefile` (in order), `envfile` and `port` lines; rollback creates and starts the Compose project from its folder with those files and that env file | Rollback starts the stopped workloads only |
| `install.json` | `controlPlaneVolumes` | Its data volumes (`migrate control-plane` prints them as `volume <name>`) | Rollback brings back what is still there |
| `install.json` | `legacyWebhookPaths` | The 0.1.x webhook paths, `{token}` where a deploy webhook's token goes: `{ deploy, github }` (each a path or a list), a list of paths, or `[{ kind, path }]`. A path without `{token}` is the GitHub App's only when its key or kind names GitHub. 1.0's own `/api/v1/` paths are never taken | Only 1.0's own webhook addresses answer |
| projects, environments, services, deployments, servers | `legacyConsolePath` | Where 0.1.x showed the object (29a.9.1), kept without host, query or trailing slash; a deployment that wasn't imported leads to its service | Old console links show "Page not found" |

## Import rules (spec 29.5)

- **One transaction.** A dry run is the real import rolled back at the end, so its report is exactly what the import does. Each record runs in its own savepoint: a record 1.0 refuses is listed with its reason and the rest go on.
- **Refs.** What each ref became is kept in `migration_record`. Refs are stable across exports of one install and opaque (29a.1), so a second import of the same bundle, or of a newer export of the same install, finds every record already imported and changes nothing; the dry run says "N already imported".
- **Labels** (29a.6) are read by `migration/labels.ts`: roles, kinds, sources, mounts, builders, hostname sources, channel kinds with each kind's setting and secret labels, events ("Nearzero backup" has no 1.0 event), deployment statuses and triggers (Tag, Redeploy, Preview and Rollback are recorded as push or manual), data and registration modes. Capabilities and Agent policies match the labels of spec 4.7 and 19.9 (an explanation in brackets on 1.0's side is ignored) or 1.0's keys. An unknown label is reported and 1.0's default used.
- **Notes.** Every entry of the manifest's `notes` is listed under "Not in Nearzero 1.0".
- **Order.** People, workspaces, SSH keys, servers, Git providers, DNS zones, uploaded certificates, each server's certificate authority store (`acme/host/acme.json`, `acme/<server ref>/acme.json`, read as Traefik keeps it), destinations, channels, projects, environments, services, hostnames, backup schedules, tasks, deployments, access policies, members, invitations, Agent sessions, install settings, then the move plan. Imported schedules wake the task and backup schedulers.
- **Host bind mounts.** An application that ran on the Nearzero host with bind mounts keeps them: the import records them, in that definition (source, builder, commands, bind mounts), as an administrator's approval (`host_approval`), so the move's deploy runs them, and the report says so; any later change needs a Nearzero administrator's deploy (spec 24 G3). A pasted Compose stack on the host keeps its privileged options the same way (`compose_stack.approved_keys`); one whose file pulls in other Compose files waits for an administrator's deploy, and the report says so. A service placed on another workspace's server is refused: "its server belongs to another workspace."
- **Names and addresses.** Workspace slugs and old slugs, server labels (`hostnameLabel`), internal app names (so other apps reach it by the same name on the private network), database data volumes (the first of `volumes`, used as it is) and passwords, public ports (libSQL's `publicPorts.http` when `publicPort` is null), generated hostnames and webhook secrets are kept when they are free on this install. A taken internal name is changed and the report says so ("its internal name … can't be used here, so it is …"). **Volumes** (29.5): a volume mount uses the volume the bundle names under that exact name: one named `<app name>-<name>` is the mount `<name>`, any other is kept as the mount's own Docker volume (`volume` beside its `name`, which editing the mounts keeps); a name in `volumes` that no mount places is reported, never replaced by an empty volume. **Public ports** (29.5) are the bundle's exactly, also outside 20000–29999 (migration `0653` lets the column hold any port; new ones still come from that range); the import never picks another, and one another 1.0 service already holds leaves the service private, reported. An app's service port is `servicePort`, else the container port its hostnames route to (3000 without one). Redis's `persistence` (29a.9) needs nothing stored: how 1.0 starts Redis reads the files the volume holds (below).
- **Secrets** are sealed with this install's key, bound to their row, as they are written: workspace keys, SSH private keys, Git provider credentials, destination keys, channel secrets, database passwords, registry passwords, file mount contents, variables, two-factor secrets, uploaded certificate keys, each server's ACME state. Another install's key opens none of them.
- **Passwords** keep their 0.1.x hash, stored as `nzlegacy1:` plus its normalized description: scrypt as 29a.5.1 declares it (`encoded` "<salt>:<key>", `params` N, r, p, keyLength, `saltEncoding: "utf8"` — the salt text's UTF-8 bytes, not hex-decoded — `keyEncoding: "hex"`, `passwordNormalization: "NFKC"`), also PHC `$scrypt$ln=…` and `scrypt:N:r:p$salt$hex`; bcrypt (`$2a$`, `$2b$`, `$2y$`, the first 72 bytes as other implementations read them) and argon2 PHC strings. The first successful sign-in replaces it with argon2id without touching the person's sessions. `unknown`, a missing hash or an unusable declaration leaves the account without a password, reported with `sudo nearzero reset-password <email>`. Banned people are left out.
- **Two-factor** secrets are sealed unchanged: `secretBase32`, or `secret` (whose UTF-8 bytes are the HMAC key) turned into base32. Backup codes arrive as SHA-256 of each unused code exactly as it was shown; at sign-in 1.0 tries its own normalized form, then the typed text as is, in capitals and in lower case. An `unreadable` secret turns two-factor off for that person, reported.
- **Capabilities and Agent policies** are matched by their spec labels (4.7, 19.9) or 1.0's keys; unknown ones are left out and listed.
- **Webhooks.** The deploy webhook's secret part (`webhookToken`) is stored as its SHA-256 with a sealed copy; `POST /api/v1/webhooks/deploy/<secret>` deploys the service, and "Replace URL" makes an `nzw1.` token as usual.
- **Dropped settings** found in the records are reported with what happens instead: replicas above one, resource limits, building on the Nearzero host, build arguments and secrets, custom commands and arguments, Compose's unique-name options, path rewriting on hostnames, libSQL's gRPC and admin ports, extra S3 client options, other sign-ins, Compose database backups (left out).
- **Invitations** get a new token (spec 29.4), sent on the first resend; expired ones are left out.
- **The first workspace** becomes the install's when the install has none, or when its own is still empty (a fresh server's owner with nothing in it).
- **Agent sessions** become turns: each person message opens one, the Agent's messages until the next are its answer with "Steps:" lines; an unknown author's session goes to the workspace owner, shared.
- **Deployments** are history: none is active (the move makes the one that runs), logs are kept line by line with `logTruncated`. The newest Running or Succeeded one per service orders the move; when the bundle carries deployments, a service with none was never deployed and stays undeployed (without deployments, creation order stands in).
- **Install settings** (29a.5.22). Platform domain, console hostname, managed zone, public address, data mode and registration mode are compared with this install and explained; the shared edge is listed as dropped; the Let's Encrypt email, request logging, the host's alert thresholds and daily cleanup are written. The installer carries the shared public settings from the old settings file itself (see below); the 0.1.x names 1.0 reads under a 1.0 name (spec 03 3.5) are one table, `LEGACY_SETTING_ALIASES` in `packages/shared/src/config.ts` (re-exported as `SETTING_RENAMES` in `migration/install.ts`) and `NZ_SETTING_ALIASES` in the installer; `installer/README.md` lists them.

## Old webhook paths (spec 29.5)

The import keeps each pattern of `legacyWebhookPaths` in `migration_webhook_path`. A POST that no console page takes is passed on by the console (`src/middleware.ts`) to the control plane as `POST /api/v1/webhooks/legacy/<old path>`, which matches it against the kept patterns (an exact path before a token pattern it would also fit, so `/api/deploy/github` isn't read as a token under `/api/deploy/{token}`) and hands the same body and headers to 1.0's own handler:

- a deploy path goes to `POST /api/v1/webhooks/deploy/<token>`, where the imported token is checked as usual (wrong: 401);
- the GitHub App's path goes to `POST /api/v1/webhooks/github/<provider id>` of the app the delivery names (`X-GitHub-Hook-Installation-Target-ID`), else each imported GitHub App in turn until one accepts the signature (none: 401);
- anything else is 404 "Nothing here takes this request.", as before.

## Volume archives (moving to another machine)

A bundle made with `export --volumes` carries `volumes/<service ref>/<volume>.tar`, each rooted at the volume. On another machine (not `--in-place`) the import keeps each one for a service it creates, in `migration_volume_archive` with its size and SHA-256, in 4 MB pieces sealed with a key derived from this install's (AES-256-GCM, bound to the archive and the piece's place). The volume is the service's new volume (a database's data volume is the one the import names; an app's keeps its name). On the server the export came from, the archives aren't needed and the report says so.

Before a service's first deploy the move restores each of its archives (`volume.restore` on its runner): the runner downloads it from `GET /api/v1/runner/migration-archives/<id>` with its own credential (only an archive of a service on that runner's server; others are 404, no credential 401), checks size and SHA-256, creates the volume when missing and unpacks the archive into it with the owners the archive gives. A restored archive is marked and never restored again. A failed restore marks the service "failed: its data couldn't be restored into the volume <name> (<reason>)" before anything is deployed, and its 0.1.x workload starts again when it was stopped; `migrate retry` tries again.

## Old console addresses (spec 29a.9.1)

The import keeps each `legacyConsolePath` in `migration_console_path` with its tail (the path without its first segment, the old workspace prefix). `GET /api/v1/migration/console-path?path=<old path>` finds it exactly, or with or without that prefix, and answers:

| Who asks | Answer |
| --- | --- |
| Signed out, the address is kept | `{ "signIn": true }` (nothing about the object) |
| A member of the object's workspace, or an instance administrator | `{ "target": { kind, workspace, projectId?, environmentId?, serviceId?, deploymentId?, serverId? } }` |
| Anyone else, an unknown address, or an object since deleted | 404 |

The console asks it when a GET finds no page (and on `/dashboard/…` addresses before its own rules): the answer becomes a 301 to the object's 1.0 page (`legacyObjectPath` in `lib/legacy-paths.ts`: a project or environment opens its overview, a service its page, a deployment its detail, a server the servers page), or sign-in first and back to the old address. The fixed old pages keep their own redirects.

## The move

The job `migration.move` (in the control plane, where the runners connect) runs `runMove` (`migration/moves.ts`) through a driver (`move-job.ts`); tests replace the driver with a fake. Targets in order: the Nearzero host, then servers by their oldest service; on each, services oldest deployed first.

1. **Prepare the target.** The host's runner must be connected (10 minutes). A remote server's `legacy` workloads stop over SSH, then setup runs again (spec 9.3) and its runner connects; on failure the old router starts again and every service on it is "failed: its server couldn't be prepared: <reason>". Then its ACME state goes into its router (`certificates.import`) and its uploaded certificates are pushed, before any of its routes switch.
2. **Each service**, in the order of 29.5: its 0.1.x workload stops (`legacy.workload stop`; a database can't share its volume; a Swarm service also lets go of its published ports, which Swarm holds even at zero replicas, kept in the label `dev.nearzero.migration.ports` as `published:target:protocol:mode` words that the runner, the installer and the server scripts all read); volume archives from the export are restored into its volumes (moving to another machine, `volume.restore`); the ports it publishes (a database's public port, an app's published ports) are waited on until nothing on the server holds them (`ports.wait-free`, up to 60 seconds); the service is redeployed through the deploy queue (trigger manual, "Moved to Nearzero 1.0") with those exact ports and waited on until it runs; its hostnames route to the new container. When a step fails, the service's 1.0 container is removed, the old workload starts again as it was, and the service is listed: "failed: port 5433/tcp is still held by the container x, so it can't be published here; its 0.1.x workload is running again", or the deploy's own reason.
3. Every step records where it got to (`migration_server_move`, `migration_move`), so the job continues after a restart: a workload is never stopped twice and a requested deployment is waited on, not requested again.

The move and its finishing step run on the worker's general lanes, apart from deploys and every other kind of long work (spec 23.2).

**Compose stacks with the same project name** (29.5). A moved stack keeps its 0.1.x project name, so its volume names stay, and 1.0's deploy may replace 0.1.x's stopped containers of that project; 1.0 never relies on them. A stack's `legacy` (29a.9) may name its `folder` (a path on its server, used exactly as given), `composeFiles` (in order) and `envFile`; the import keeps them with the move, and a stack without a folder is reported: "its 0.1.x Compose project … can't be restored from its files (the export doesn't name its folder), so a failed move or a rollback starts its stopped containers again." Whenever 0.1.x's copy must come back (a failed move, or rollback on the host or a remote server), 1.0 first removes its own labelled containers in that project with their anonymous volumes, then runs `docker compose --project-directory <folder> -p <name> -f … --env-file … up -d` (without named files, Compose's own lookup in the folder). `envFile` is a name in the folder or, where 0.1.x keeps it elsewhere, an absolute path (29a.9): that one is used only as a regular file, reached by no link, under the 0.1.x install's data folders (29a.9): on every server `/opt/nearzero` and `/etc/nearzero` (where 0.1.x keeps app, Compose and secret files on remote servers), and on the Nearzero host also the control plane's `controlPlaneDetails.folder` and the folders of its `controlPlaneVolumes`; 1.0 never writes it, and the stack isn't started without it when it doesn't qualify. A `..` anywhere, or any other absolute path, is refused; `composeFiles` stay names in the folder. The runner mounts the file's folder read-only into its short-lived Compose container (a folder that doesn't exist is never made). On the Nearzero host the runner runs Compose in a short-lived container of its own image with the folder mounted read-only at the same path. `migrate rollback-plan` prints `stackfolder`, `stackfile` and `stackenv` lines for the host's `nearzero` command. While a moved service isn't finalized, 1.0 never passes `--remove-orphans` to Compose (deploy, recovery and removal). 1.0 never changes or removes a folder named in `controlPlaneDetails` or a `legacy` entry before finalize; the one exception is the install folder itself (below).

`migrate status` reports what actually runs: each runner's state report (every 30 seconds) is kept with the runner (`runner.containers`, migration `0654`: each container's id, Docker state and service), and a moved service with no running container on its server's report from the last 3 minutes reads "<service> on <server>: moved, but nothing of it is running now", with "A moved service isn't running now: … Start or redeploy it from the console." When the server hasn't reported lately, the move's own record stands.

`migrate retry` puts failed services (and failed servers) back in line. `migrate finalize` marks the move done and starts `migration.finalize`, which removes every 0.1.x workload through the runners; volumes stay, as the 1.0 services use them.

**Data already in a moved database's volume is loaded** (29.5). Postgres, MySQL, MariaDB and MongoDB read their data folder as it is. Redis starts through a short script (`redisStartScript` in `service-runtime/databases.ts`, its password in the environment): when the volume holds a snapshot (`dump.rdb`) and no append-only files, as a 0.1.x Redis's does (`persistence` Snapshot, the default), it starts with append-only off so it loads the snapshot, then turns append-only on from the loaded data (`CONFIG SET appendonly yes`, which writes the append-only files); otherwise, and on every later start, it starts with append-only on. The image's own entrypoint still starts the server, so it runs as the image's user.

## Command line

Inside the control-plane container (`nearzero-control`, also `bun apps/control/src/cli.ts`); the passphrase comes from `NEARZERO_MIGRATION_PASSPHRASE` or a terminal prompt, and `-` reads the export from standard input.

| Command | Does | Exit |
| --- | --- | --- |
| `import [--dry-run] [--in-place] [--no-deployments] [--wait] [--json] <file\|->` | Prints the report; a real import starts the move ("Follow it with: sudo nearzero migrate status"), `--wait` prints one line per service as it ends ("web on prod-1: moved", "api on the Nearzero host: failed: <reason>") | 0; 1 refused; 3 some services failed (with `--wait`) |
| `migrate status [--wait] [--json]` | Where the move stands, one line per service | 0, or 3 with `--wait` when some failed |
| `migrate retry [service id…]` | Failed services again | 0; 4 finalized |
| `migrate finalize --yes` | Marks it final, removes the 0.1.x workloads; refused while services move | 0; 1 |
| `migrate rollback-plan` | The host's 0.1.x workloads to start again, `kind name` lines | 0; 4 finalized |
| `migrate rollback-servers` | Remote servers back to their 0.1.x workloads over SSH (runner stopped, 1.0 containers stopped) | 0; 3 some failed |
| `migrate control-plane <file\|->` | The 0.1.x control plane's workloads (`kind name`), volumes (`volume name`) and details (`project name`, `folder path`, `port n`) | 0 |

`sudo nearzero` on the host (spec 03 3.4):

- `import [--dry-run] <file>` streams the file into the control plane (a new machine: services deploy fresh; volume archives from `--volumes` aren't restored yet, and the report says so).
- `migrate status`, `migrate retry`.
- `migrate rollback [--yes]` asks "Go back to Nearzero <version>? …", sends remote servers back, then in the order of 29.5: (1) removes only what carries 1.0's label: its compose project's containers (`down`, never `--volumes`), every container labelled `dev.nearzero.edition=1` (router, runner, moved services), and the volumes and networks labelled with this move's attempt (`dev.nearzero.migration-attempt`, kept in `/opt/nearzero/migration/attempt`), which includes the 1.0 database volume the attempt made; a volume named in the bundle (`keep` and `volume` lines of `migrate control-plane`) or without 1.0's label is never removed; (2) sets 1.0's files aside under `/opt/nearzero/migration/1.0-<time>`, puts the 0.1.x settings, files and `nearzero` command back, creates and starts 0.1.x's Compose project from its folder (`controlPlaneDetails`) whether or not any of its containers are left, with its own Compose files in order (`-f` for each of `composeFiles`) and its env file (`--env-file`, `envFile`), or Compose's own file lookup when the bundle names none, then starts every `controlPlane` entry; (3) starts each moved service's 0.1.x workload as it was (a Swarm service with its replica count and published ports); (4) waits up to 5 minutes until the 0.1.x console answers on one of its ports (`/login`, `/sign-in`, `/signin` or `/` answering 2xx or 3xx) and every PostgreSQL of its control plane takes connections (`pg_isready`), then prints "Nearzero <version> is back. The move to 1.0 was undone.", or names what didn't come back and exits 1. Refused after finalize: "The move is finalized: the 0.1.x data is deleted, so it can't be rolled back." It works even when 1.0 never finished starting.
- `migrate finalize [--yes]` asks to type "delete", then removes, item by item, the 0.1.x control plane's workloads and volumes and the host's stopped 0.1.x workloads (the control plane removes the other servers' through their runners), deletes `/opt/nearzero/migration/0.1`, and waits up to 2 minutes for them to be gone: "Finalized: the 0.1.x data is deleted. Nearzero 1.0 keeps running.", or "… Still being removed: <names>." with how to check them. Nothing carrying `dev.nearzero.edition=1` is touched, and a Compose project is never removed as a whole: a moved stack keeps its project name (so its volume names stay), so only the project's unlabelled containers go. Each container goes with its anonymous volumes, never a named one. Last, each network the removed workloads used (0.1.x's shared and router networks, its Compose default network, a moved stack's old default network) is removed once no container is attached and it carries no 1.0 label; Docker's own networks stay.
- `export` answers that this server runs 1.0 and how to import an export from elsewhere.

## The installer

`NZ_LEGACY_FINAL_VERSION` (one constant) is the final 0.1.x release.

1. **Found.** `/opt/nearzero/.env` names a `0.1.*` version; or, for releases before the final one (which write no version), it names no version, lacks 1.0's marker `NEARZERO_EDITION=1` (every 1.0 install writes it) and a 0.1.x control plane is running or present: a container or Swarm service named `nearzero…` without 1.0's `dev.nearzero.managed` or `dev.nearzero.component` label. Another version is a 1.0 install. An older version stops: "This server runs Nearzero <v>. Update it to <final> first: curl -fsSL https://cdn.nearzero.dev/v<final>/install.sh | sudo bash. Then run this install command again." So does a `nearzero export --version` that doesn't print `1`, and an export that exits 2.
2. **Asked.** On a terminal it explains and asks "Move this install to Nearzero 1.0? Your apps restart once, briefly; data, addresses and passwords are kept. [y/N]". Without one it needs `NEARZERO_MIGRATE=yes` and `NEARZERO_MIGRATION_PASSPHRASE` (16+ characters). No admin account is asked for: the accounts come from the export. A dry run (`NEARZERO_DRY_RUN`) says what a real run would do.
3. **Settings.** The 0.1.x public settings 1.0 reads under the same names are carried (public IP, bind address, ports, platform domain, console hostname, ACME email, managed zone and its email, strict host keys, metrics retention and refresh, time zone, trusted proxies and origins, console URL, instance email, registration mode, builder image overrides, DNS address and port), and the renamed ones of spec 3.5 under their 1.0 names; internal ones (database, secrets, images) are made fresh.
4. **Export.** `nearzero export` with the passphrase in its environment; the last line `NEARZERO_EXPORT_OK <path> <sha256>` is checked against the file. A generated passphrase is shown once: "Keep this passphrase: you need it to undo the move."
5. **Check.** The 1.0 images are pulled; a temporary database (`nearzero-migration-db` on `nearzero-migration-check`, removed afterwards) takes the dry-run import, whose report is printed; on a terminal "Continue with the move? [y/N]".
6. **Stop and set aside.** The control plane's workloads stop (the `kind name` lines of `migrate control-plane`; its `volume`, `keep`, `project`, `folder` and `port` lines are never treated as workloads; a Swarm service lets go of its published ports too; apps keep running); `.env`, the `nearzero` command and any of `compose.yml`, `router`, `dns` go to `/opt/nearzero/migration/0.1`. Ports 80, 443, 4321 and 3000 must be free now; otherwise everything is put back and started again. The 1.0 `nearzero` command is installed at once, so `migrate rollback` works whatever happens next.
7. **Install, import, move.** 1.0 starts, the export streams into `import --in-place`, and `migrate status --wait` prints a line per service. The summary says how to go back and how to finalize.

A run that stopped half way (state `moving`) is refused with "Go back to 0.1.x with: sudo nearzero migrate rollback. Then run this install command again."

### 1.0's own names and label (spec 29.5 "No shared names with 0.1.x")

1.0's install folder is `/opt/nearzero`, which can also be the 0.1.x control plane's folder (`controlPlaneDetails`). The move must put 1.0's `.env` there, so it sets aside only the files it replaces (`.env`, and any `compose.yml`, `router` and `dns`) under `/opt/nearzero/migration/0.1` and rollback puts them back as they were; nothing else in that folder is changed or removed before finalize.

The names are fixed for every 1.0 install, moved or fresh, and none is 0.1.x's: the Compose project `nearzero1`; the containers `nearzero-control`, `nearzero-runner`, `nearzero1-postgres` (the bundled database; `DATABASE_URL` names it) and `nearzero1-dns` (the runner's DNS server uses the same name); the runner's `nearzero-router`; the networks `nearzero-internal` and `nearzero-edge`; the volumes `nearzero-postgres-data`, `nearzero-runner-state`, `nearzero-runner-handoff` and the runner's `nearzero-router-certificates`. The networks and volumes are created by the installer (external in the compose file), so no compose run adopts, recreates or deletes one.

Everything 1.0 creates carries `dev.nearzero.edition=1` beside `dev.nearzero.managed=true`: the compose file's containers, the installer's networks, volumes and check database, and every container, volume, network and image the runner makes (its Docker client adds it); while a move runs, also `dev.nearzero.migration-attempt=<attempt>` (`NEARZERO_MIGRATION_ATTEMPT` in `.env`, cleared on the next run that isn't a move). Rollback and uninstall remove only what carries the label (uninstall: the label or the project `nearzero1`).

Before anything starts, the installer checks each of these names: one that exists without 1.0's label stops the run: "Nearzero 1.0 needs these names, and this server already has them without Nearzero 1.0's label, so nothing was changed: - the network nearzero-edge …". On a rerun of a 1.0 install made before the label existed (not a move), `dev.nearzero.managed=true` counts as 1.0's, and that install's containers in the old project `nearzero` that carry 1.0's component label are removed before the new ones start, so two databases never share a volume.

## The final 0.1.x release must provide

`sudo nearzero export [--out <file>] [--no-deployments] [--volumes]` and `--version` exactly as spec 29.2a, a bundle as spec 29a, its version as `NEARZERO_VERSION=<version>` in `/opt/nearzero/.env`, and, for the move in place to stop and restart its workloads, the fields in "What the import uses beyond spec 29a" (the control plane's workloads above all).
